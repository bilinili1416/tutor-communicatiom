# 吴健雄学院导师交流预约助手

面向东南大学吴健雄学院「导师制 · 在线预约」页面的预约辅助脚本。

**当前进度：第二阶段已完成，默认处于「未武装」状态。** 不点武装按钮，脚本就只做只读查询，不会发出任何写请求。

## 它能做什么

第一阶段（只读）：

- 定位目标批次、主讲人与场次
- 用响应头 `Date` 估算本地时钟与服务器时钟的偏差
- 判定报名状态（已预约 / 已满 / 未开始 / 已结束 / 可预约 / 已预填写）
- 打印「如果此刻提交，会发出什么请求」

第二阶段（需显式武装）：

- 预填写（`sfzc=true`）：把手机号提前暂存到目标场次
- 到点自动提交（`sfzc=false`）：在报名开始的瞬间反复尝试，直到成功
- 命中后回读确认，并立刻停手

## 两套前端

这个模块有两套互相独立的前端，接口和状态码都不一样。脚本按「前端适配器」分别建模，面板会自动识别当前在哪一套上，并在报告第一行标出来。

|  | 桌面版（layui） | 移动 / 微信版（Vant） |
|---|---|---|
| 页面 | `/wjx/zxyy/xs` | `/wjx/wx/zxyy/zx` |
| 列表接口 | `POST zxyy/xs/ajaxList`，参数 `pc.id`、`ds.name` | `POST wx/zxyy/zx/ajaxList`，参数 `page`、`limit`、`name`、`pcId` |
| 提交接口 | `POST zxyy/xs/apply` | `POST wx/zxyy/zx/apply` |
| 提交参数 | `zxxx`（场次 ID）、`sjhm`、`sfzc` | 同上 |
| 状态码 | `yyzt`：0 已预约 / 1 已满 / 2 未开始 / 3 已结束 / 4 可预约 / 5 已预填写 | 前端推算：1 已预约 / 2 已满 / 3 未开始 / 4 已结束 / 5 可预约 |
| 数据形态 | 一行一个场次，行里带 `ds`（主讲人）和 `pc`（批次） | 一位导师一个对象，场次在 `zxList` 里 |
| 批次来源 | `POST common/selector`，`clazz=ZxyyPc` | 页面全局变量 `pcs` |

**后台外壳（`/wjx/admin`）里用的是桌面版。** 从左侧菜单进「在线预约」时，内容区 iframe 加载的就是 `/wjx/zxyy/xs`。

鉴权只需要 SESSION cookie；`.me` 模块参数由页面自己的 `$.ajax` 包装自动补上——读接口沿用页面包装，写接口则手动补 `.me`。

## 安装与使用

1. 浏览器安装 Tampermonkey（或兼容的 userscript 管理器）
2. 新建脚本，把 `src/seu-wjx-tutor-dryrun.user.js` 的内容整个粘进去并保存
3. 登录学院微服务平台，**进入「导师制 → 在线预约」**（不是停在后台首页）
4. 右下角出现面板，选批次、填主讲人、填手机号

### 第一阶段：先看清楚再动手

- **单次扫描**：只读一次，把状态、名额、报名窗口和「将要提交的请求体」打出来
- **开始监视**：按间隔反复扫描，状态变化时才追加一条记录（每条都带 `[本机时间 | 服务器时间]`）

### 第二阶段：预填写与到点提交

1. **设为目标** —— 会先重新扫描一次，再用那次结果当目标（避免拿过期数据去武装）
2. **[可选] 预填写** —— 把手机号提前暂存，开放时就能省掉现场填写
3. **武装：到点自动提交** —— 会弹出确认框，列出目标、接口地址和完整请求体
4. 到点前**保持这个标签页在前台**。后台标签会被浏览器降频，可能错过边界
5. 成功后脚本自动停止并回读确认；任何时候点「停止」都会立刻收手

配置（包括手机号）存在浏览器 `localStorage` 的 `jxzx.dryrun.config.v1` 里，面板上的「清除配置」可以删掉。**「已武装」状态不写入存储**，刷新页面即回到未武装。

## 触发时机是怎么定的

实测下来，这台服务器的时钟比标准时间快约 230 秒（同时对比百度和 Cloudflare 的 `Date` 头，本机时钟是准的）。但**还不知道服务端到底用哪块表判定「报名开始」**：

- 如果它用自己那块表，真正的边界是 `bmkssj` 本身
- 如果它用标准时间，真正的边界是 `bmkssj + 230 秒`

所以脚本把**两个候选边界都覆盖**：从第一个边界起试探，一直重试到第二个边界之后 30 秒。不需要事先知道答案，代价是最坏情况下多打几十个请求。

唤醒节奏按距离分档，最长 10 分钟一次；**离第一个边界还远时只做只读探活（顺便重新校时），一个 apply 都不发**——所以提前几小时武装也不会攒出一堆无效报名记录。进入边界前 2 秒才切换成真正提交，临近时加密到 200 毫秒一次，越过边界后逐步退避。

## 安全设计

- **默认未武装**：不点按钮就没有任何写请求，第一阶段那条红线默认成立
- **武装不持久化**：刷新即失效，避免「忘了它还开着」
- **确认框会列出完整请求体**：武装和预填写都要确认
- **命中即停**：拿到 `code:0` 立刻停手并回读确认
- **会话失效即停**：收到 `code:-100 / -99` 直接停下并提示重新登录，不做无意义重试
- **写请求用 `fetch` 直发**：绕开页面 `$.ajax` 包装的两件事——`code != 0` 时弹 `layer.alert`（重试几十次会糊满弹窗），以及相同请求去重

## 测试

```
node tests/dryrun.test.mjs
```

38 项断言，在一个最小的 DOM 模拟里跑真实脚本源码，两套前端各自的真实响应结构都作为夹具。第二阶段有时序逻辑，所以测试带一个**虚拟时钟**，可以确定性地验证：

- 边界 3 秒之前一个 apply 都不发（远处只做只读探活）
- 第一次 apply 落在第一个候选边界 ±3 秒内
- 尝试覆盖到第二个候选边界（服务器用标准时间的情况）
- 成功之后立刻停手、不再发请求
- 用户在确认框点取消时不会武装
- 未武装时空闲状态不产生任何写请求

## 还没验证的事

- **成功提交一次都没发生过。** 写链路本身已经验证过：对已满/已结束的场次提交，服务端会返回业务错误而不是权限错误，说明地址、`.me`、会话三者都对
- 服务端到底用哪块表判定开放时间（已知它**强制校验**报名时间，见下）
- 名额并发是否原子
- 是否存在频率限制或风控

另有一条来自使用者经验、我们尚未实测：**场次在报名开放前就已经发布在列表里**（按以往几期的规律）。如果成立，就意味着「提前设目标 → 预填写 → 武装」这套准备流程在开放前是完整可用的。

## 已验证：服务端强制校验报名时间

对窗口外的场次提交，服务端返回：

```
{"code":-1,"msg":"预约失败：不在可报名时间【2026-09-29 12:30至2026-09-29 13:30】内。","success":false}
```

三点结论：

1. 时间窗口是**服务端**判定的，不是只有前端拦着 —— 所以不可能提前抢跑
2. 拒绝时给的是干净的业务错误，不是权限或风控拦截
3. 这条消息把窗口起止原样报了出来，可以直接和 `bmkssj` / `bmyxsj` 对照
